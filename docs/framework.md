# 记忆摄取评测框架 v0.6

- 框架文档版本：v0.6；现行产物的 `standard_version=v0.4` 是数据格式标识，文档版本另行记录。规则变更时升版本号，记入仓库根目录的 [CHANGELOG.md](../CHANGELOG.md)，并复核受影响的样本。
- 现行评测采用 6.4 节的拆分判定，只报告漏记率和误记率。
- 本文件只规定**怎么评**：单元怎么切、提交项怎么判、指标怎么算、统计怎么做、标注怎么组织。它不规定**什么该记**。
- “什么该记”由**入库政策**规定，单独成文（见 `policies/`）。每次评测都必须声明使用哪一份政策、哪个版本。同一个系统换一份政策，分数可以完全不同；不同政策下的结果不能放在一起比较。
- 适用范围：只评**摄取**，即给定一段会话，被测系统提交的记忆条目对不对、全不全。读取、检索、审核一致率、成本精算都不在本框架内。

## 1. 评什么

被测系统读完一段会话，提交一组条目 **D**。标注者依照所选政策，事先从同一段会话里盲标出一组**应记单元 U**和一组**边界负例 N**。本框架回答三个问题：

1. **漏记**：U 里有多少单元没有被完整覆盖？
2. **误记**：拆分判定中，D 里的陈述有多少无会话依据或写歪原意？政策价值判断单列，不并入误记率。
3. **属性质量**：逐条映射协议另外核对被覆盖单元的类别、范围和条件；拆分报告不计算这些属性准确率。

## 2. 入库政策必须提供什么

一份政策是一个 Markdown 说明加一个机器可读的 JSON（字段名以 JSON 为准），至少包含：

| 项 | 内容 |
|---|---|
| `id` / `version` | 政策标识和版本 |
| 核心判断 | 一段话说明什么样的信息值得记 |
| `categories` | 应记单元的类别，每类附定义、证据要求和至少两个判例 |
| `attributes` | 除类别外，单元还要标注、并在评分时核对的属性（如来源依据），每项列出取值和约束 |
| `reject_reasons` | 不该记的原因码及定义 |
| `condition_types` | 条件的类型（见 4.2 节） |
| `scope_values` | 范围的取值形式 |
| `superseded` | 会话中被推翻的旧状态怎么处理：`final_state_only`（只记最终状态，旧状态作为负例），或 `keep_history`（旧状态也算应记单元） |
| `flags` | 可选。每条提交项额外判定的标记，**只单独报告，不计入主指标**（如“是否含秘密值”） |
| 切分示例 | 至少 5 个“一段原话 → 切成几个单元”的示例 |

政策的写法应当足以让两个不熟悉这个政策的标注者，对同一段会话给出基本一致的结果。做不到的，先修政策，再开始标注。

## 3. 被测系统的接口（所有系统统一）

### 3.1 输入

- 只有一份 `transcript.md`：从原始会话记录提取，带轮次编号；包括用户和助手的发言、工具调用的名称和参数；工具输出超过 2000 字符的部分截断，并标出截断位置。
- 头部写明会话 id、来源、日期、工作目录（cwd）、总轮数，以及 **`project`：会话实际所属的项目，由标注者在盲标时填写**（一段会话涉及多个项目时逐个列出）。cwd 只作参考。范围类属性的判定以 `project` 为准。
- 被测系统**从空记忆库起跑**；会话之间互不影响；被测系统不能访问 gold。
- **模型固定**：同一次评测中，所有被测对象使用同一个 LLM（名称、版本或快照相同）和同一个向量模型；无法指定向量模型的产品单独注明处理方式。
- **生成参数按产品默认**：温度、思考开关、最大输出长度等保持各被测系统按官方文档做最少配置时的默认行为，不统一改写；每次调用实际发出的参数逐条记录（见 12.3 节）。产品必须填写才能运行的参数（例如向量维度），按官方文档填写并记录。
- 标注和判定使用的模型另外固定（见第 5 节第 6 条），并且不应与被测对象使用的 LLM 相同。

### 3.2 输出：每个提交项一个 JSON 对象

以下结构用于逐条映射协议（6.1～6.3）。拆分判定（6.4）只要求每条记忆提供非空 `draft.statement`；适配器保留原文，其他字段不从 gold 补写。

```json
{
  "statement": "一句话写清这条信息，包含条件",
  "category": "<政策定义的类别>",
  "attributes": {"<政策定义的属性>": "<取值>"},
  "scope": "<政策定义的范围>",
  "conditions": [{"type": "<政策定义的条件类型>", "text": "..."}],
  "evidence": [{"turn": 30, "quote": "原文"}]
}
```

- **一个提交项只写一个单元**；同时覆盖多个单元的，判为 `bundled`（见 6.2）。
- 被测系统的原生格式不同的，由适配层转换；转换不了的字段留空。**字段缺失时，该项判错，不跳过。**
- 适配层只做格式转换，不补内容、不改写措辞。

## 4. 应记单元

### 4.1 通用切分规则

以下规则与政策无关；政策可以在此基础上补充，但不能违背：

1. **一个单元是一条能独立使用的信息。** 同一回合里说了几件互相独立的事（判断方法：拿掉其中一件，另一件仍然成立），就切成几个单元。
2. **条件是单元的一部分，不拆成独立单元。** 适用范围、时效、是否只限这一次、执行前是否需要确认、适用于哪类操作、理由，都写进单元的条件。〔参考：Memory Trap〕
3. **证据必须指向原文**：轮次编号加原文引文。不能引用会话里没有的内容。
4. **后面的表态不能倒灌到前面**：一件事在第 30 轮才确认的，证据就记在第 30 轮。〔参考：DyadMem〕
5. 会话里引用了之前的上下文，但这段上下文本身不在 transcript 里的，标为 `prior_context`：**不进 U，也不进 N**；提交项若涉及这类内容，单独统计为“依赖外部上下文”。
6. 拿不准的单元标 `uncertain: true`（见 4.4）。

### 4.2 条件

- 条件按政策定义的类型结构化，每条再标 `key: true/false`。
- **丢了关键条件，单元判为部分覆盖；只丢次要条件，单元仍算完整覆盖**，只计入条件保留率。同一个缺陷不罚两次。（把局部许可写成通用许可，按 `distorted` 判。〔参考：Memory Trap〕）

### 4.3 单元字段

```json
{
  "unit_id": "s012-u03",
  "category": "<政策类别>",
  "attributes": {"<政策属性>": "<取值>"},
  "statement": "一句话写清，包含条件",
  "conditions": [{"type": "<政策条件类型>", "text": "...", "key": true}],
  "scope": "<政策范围>",
  "evidence": [{"turn": 30, "quote": "原文"}],
  "uncertain": false,
  "origin": "blind",
  "note": "裁定理由"
}
```

- `origin`：`blind` 表示盲标时标出的；`added_by_run:<system>` 表示揭盲后补进来的（见 6.3）。
- 边界负例 N 用同样的结构，把 `category` 和 `attributes` 换成 `reject_reason`（政策定义），并加 `layer: random | targeted`，区分来自随机抽样的会话还是定向构造的样本。

### 4.4 uncertain

- **漏记率同时报告两个口径**：排除 uncertain 的，和把 uncertain 全部计入的。
- uncertain 超过该批 U 的 15% 时，触发政策复审。这说明政策写得不够清楚，问题不在单元本身。

### 4.5 长会话

- 超过 300 轮的会话，按话题或时间切成多段，切点记在 transcript 里，每段作为一个样本；各段沿用同一个会话 id。
- 每个样本记下轮数；所有指标按会话长度分层报告（≤50、51~150、>150 轮）。

## 5. 标注流程

1. **盲标**：只读 transcript，依照政策标出 U 和 N，填写 `project`，写下证据和理由。**这一步不看任何系统的提交项。**〔参考：Hamel〕
2. **冻结**：冻结 U 和 N，记录冻结时间、框架版本和政策版本。冻结之后，不能悄悄修改原有单元。
3. **揭盲判定**：打开被测系统的 D，按第 6 节逐条判定。
4. **复标**：试标阶段固定抽 20% 的会话，间隔至少 3 天、打乱顺序后重新盲标，报告单元切分（单元数、对应关系）和标签的自一致率。只有一名标注者时，这是唯一能做的一致性度量。有多名标注者时，另报告标注者之间的一致率（Cohen's κ 及原始一致率）。
5. **版本**：每个样本都记下按哪个框架版本、哪份政策的哪个版本标注。任何一边改了，都要回头复核受影响的样本；不同版本的标签不混在一起计算。〔参考：EvalGen〕
6. **标注者可以是人，也可以是模型**。模型在这里代替人工做标注和判定，属于评测集的加工，不是被测对象，不受 3.1 节“模型固定”的约束，但要满足：
   - 写明标注者和判定者的身份：人工写人数；模型写名称、版本或快照、提示词版本。
   - 模型标注同样要盲标：先标金标、冻结，再接触任何被测系统的输出。
   - **人工校准**：随机抽一部分样本由人工独立标注（判定同理），报告模型与人工的一致率（单元切分的对应率、标签的原始一致率和 Cohen's κ）。一致率达不到要求的维度，相应指标不公布。
   - 标注模型和判定模型不应与被测对象使用的 LLM 相同。
   - 人工标注时，不让模型预标 U，以免带偏标注者；模型可以帮忙提取 transcript、切分轮次、整理格式。

## 6. 提交项怎么判

### 6.1 逐条判定

| 字段 | 取值 |
|---|---|
| `covers` | 对应的单元 id **列表**（可以为空） |
| `coverage` | 对每个对应的单元分别判：`full` 完整 / `partial` 缺了关键条件或主体 / `distorted` 意思被改了〔参考：Memory Tax〕 |
| `bundled` | 一个提交项对应不止一个单元时为 true |
| 属性是否正确 | 政策要求核对的每项属性（类别、范围及 `attributes` 中各项）分别判；字段缺失的判错 |
| `matches_negative` | 如果对应的是 N 里的某条负例，填负例 id。一个提交项可以同时对应 U 和 N（例如一条总结把应记的内容和一次性的指令写在一起）：对 U 照常计覆盖，负例计入负例误收率，但因为含有有效内容，不计为误记；这类提交项通常也是 bundled |
| 政策的 `flags` | 逐项判定，只单独报告 |
| 什么都对应不上时 | `false_positive`（附政策原因码），或 `gold_miss`（见 6.3） |

### 6.2 单元的覆盖状态

- **一个单元的覆盖状态，取所有对应它、且不是 `distorted` 的提交项的并集来判。** 几个提交项合起来把主体和关键条件都写全了，就算完整覆盖。
- `distorted` 的提交项不参与并集，计入误记。
- **重复**：一个提交项放进并集后，没有带来任何新信息（单元状态没有提升，主体和已保留的条件也都没有增加），才算重复。
- `bundled` 的提交项：对它覆盖的每个单元分别计覆盖；在误记率和重复率里只算 1 条；另外单独报告 `bundled` 的比例。

### 6.3 gold_miss

- 揭盲后发现某个提交项确实该记，但盲标时漏掉了：判为 `gold_miss`，补进 U，标 `origin: added_by_run:<system>`。
- **主指标只用盲标 U（`origin: blind`）计算。** 补进来的单元单独报告：它们恰好就是被测系统自己提出来的，算进主指标等于送分。
- 每补进一个单元，所有已经判过的系统都要按新的 U 重新复核，金标的修订号加一。

### 6.4 拆分判定（另一种判定协议）

6.1~6.3 节是“逐条映射”协议：每个提交项对应到哪些单元、覆盖到什么程度。它信息最全，但要求判定者一次处理整段会话、全部单元和全部提交项，而且误记率、重复率按条数计算，**被测系统导出的粒度不同时**（例如一个系统把整段会话整理成一页，另一个系统拆成上百条）横向不可比。

拆分判定把判定拆成两种互相独立的小判断，与导出粒度无关：

- **召回判断**：给定一个应记单元和该系统导出的**全部**记忆，判断能否从这些记忆中得出这个单元、关键条件是否保留：`full`（完整）/ `partial`（缺了关键条件或主体）/ `none`（没有）/ `distorted`（写歪了）。不需要原始会话。
- **精确判断**：给定一条记忆和原始会话，先把记忆拆成原子陈述（一个陈述只表达一个可核对的事实、偏好、决定或计划；记忆中原样附带的会话原文整体算一个陈述），再判断每个陈述有依据、部分有依据、无依据还是写歪，并判断整条记忆是否明显不值得长期记（`worth`：`yes` / `no` / `unclear`）。

对应的指标：

| 指标 | 定义 | 分母 |
|---|---|---|
| 漏记率 | 召回判断为 partial / none / distorted 的单元 ÷ 单元总数；另报“完全没记住率”（none 或 distorted） | 盲标 U 中 `uncertain=false` 的单元（另报计入 uncertain 的口径） |
| 误记率 | 无依据或写歪的陈述 ÷ 陈述总数；部分有依据的陈述单列，不计入误记 | 该系统导出的全部记忆中的全部陈述 |
| 不值得记占比 | 精确判断中 `worth = no` 的记忆 ÷ 记忆总数 | 该系统导出的全部记忆 |
| 粒度 | 每段平均陈述数、记忆条数、每条平均长度 | — |

“不值得记”取决于政策；被测系统通常拿不到评测用的政策，所以这一项只单列报告，不并入误记率。拆分判定不报重复率、bundled、属性准确率和单元级 F1。两种判断都可以单独重跑、单独做人工抽检（第 5 节第 6 条）。选用哪种协议，报告里必须写明。

## 7. 指标（逐条映射协议）

本节适用于 6.1~6.3 节的逐条映射协议。拆分判定的指标见 6.4 节；7.4 节中的身份与样本来源要求，以及第 8 节中的会话聚类 bootstrap，对两种协议都适用。

### 7.1 主表（必须一起报告，不能只引用其中一项）

| 指标 | 定义 | 分母 |
|---|---|---|
| **漏记率** | 没有被完整覆盖的单元 ÷ 单元总数；“完全没覆盖”和“部分覆盖”分开报告 | 盲标 U 中 `uncertain=false` 的单元（另报计入 uncertain 的口径） |
| **误记率** | `false_positive` + `distorted` 的提交项 ÷ 提交项总数 | **全部提交项**〔参考：HaluMem 反例〕 |
| **重复率** | 重复的提交项 ÷ 提交项总数 | 全部提交项 |
| **单元级 F1** | 召回 = 完整覆盖的单元 ÷ U；精确 = 既非误记也非重复的提交项 ÷ D | — |

单元级 F1 用来防止系统靠交得极少或交得极多去刷某一项指标。

### 7.2 属性质量（以单元为分母，每个单元取覆盖它的最好的那个提交项）

- 政策要求核对的每项属性分别报告准确率，分母是被覆盖的单元。
- 条件保留率按条件类型分别报告，分母是被覆盖且带该类条件的单元。

### 7.3 负例与其他

- 边界负例误收率 = 对应到某条负例的提交项 ÷ N，按 `random` 和 `targeted` 两层分开报告。对应到负例的提交项同时计入误记率，两边互相标注。
- “依赖外部上下文”的提交项数量，单独列出。
- 政策 `flags` 中的每一项，报告数量、占比和明细；不计入误记率和 F1。
- U 为空的会话照样保留：参与误记率计算，不进漏记率的分母。

### 7.4 报告规则

- 逐条映射协议按类别、会话长度分层。现行拆分评分脚本提供来源层（by_layer）和逐样本计数，不生成类别或长度分层。
- 随机样本和定向构造的样本分开统计。〔参考：evals-skills〕
- 每份报告都注明框架版本、政策 id 和版本、样本数；标注者和判定者（人工人数，或模型名称、版本、提示词版本）及人工校准的一致率；被测对象使用的 LLM 和向量模型（名称、版本、关键参数）。

## 8. 统计

- **所有区间都用 cluster bootstrap**〔参考：通用统计〕：按 `gold.session_id` 重采样，1 万次，取 95% 区间。普通会话以会话为单位；HaluMem 转换器把同一源用户的多个 session 赋予同一标识，因此按源用户聚类。同一会话里的单元和提交项高度相关，按单条计算区间会偏窄。Wilson 区间只作参考。
- 逐条映射协议可在同一批会话的盲标 U 上做 McNemar 配对检验，列出改善和退步的单元。现行拆分评分脚本不自动计算配对显著性，区间不用于生成总排名。
- 没看到错误不等于错误率为零；样本少时一律报告区间。

## 9. 抽样

- **试标**：20~30 段，从真实会话中随机抽取，先去掉纯机械操作的会话（只跑命令、没有任何讨论的）。目的：估算标注成本、磨合政策、完成复标。
- **金标规模建议**：约 100 段〔参考：Hamel〕。以随机样本为主，再补一批定向的边界样本；边界样本要覆盖哪些组合，由政策列出。
- 记录会话长度和来源的分布，避免样本只集中在短会话或单一来源。
- 真实会话只保存在本地，不公开。可以公开的数据集必须脱敏，或者使用合成数据。

## 10. 数据格式

```
policies/<policy_id>-<version>.json   # 机器可读的政策
policies/<policy_id>-<version>.md     # 政策说明
data/<sample_id>/
  transcript.md                       # 头部含 project（标注者填写）、cwd、轮次编号、切段点
  gold.json                           # U、N、冻结时间、框架版本、政策 id 和版本、复标记录
  runs/<system>-<version>.json        # 被测系统的提交项 D（每项含记忆正文 draft.statement）
  judgments/<system>-<version>.json   # 判定结果（拆分判定为召回判断和精确判断）
```

评分脚本读取政策、`gold.json`、`runs/*.json` 和判定结果，输出汇总指标、逐样本计数和失败记录。拆分精确判断每条记忆至多列出 10 项错误摘要，保留在 judgments 文件中；报告用输入哈希清单定位原始判定。

## 11. 试标需要验证的问题

- 每段会话标一遍需要多久？100 段的总成本能否接受？
- 复标的自一致率有多高？切分规则够不够硬？
- 政策里的原因码和条件类型够不够用？uncertain 的比例会不会超过 15%？

## 12. 可复现性

一次评测的结论，要能被别人做两件事：**原样复核**（拿留存的产物重新评分，得到完全相同的数字），以及**重做加工**（用同样的模型和提示词重新标注、判定，和留存结果比一致率）。模型的输出不是确定的，所以产物必须留存，过程参数必须记全。

### 12.1 外部数据：固定版本，不随仓库分发

- 每个外部数据集一份清单：数据集 id、来源地址、**固定的 revision**（如 HuggingFace 的 commit SHA）、所用文件的路径和 sha256、许可证、访问条件（是否需要申请）。
- 下载只按清单里的 revision 拉取，下载后校验 sha256，不一致就报错，不用“最新版”替代。
- 原始数据默认不进仓库，即使许可允许：原始会话可能含个人信息，各数据集的许可和访问条件也不同，统一用“固定版本 + 自行下载”处理。

### 12.2 加工产物：按许可决定是否公开

- transcript、金标、提交项、判定都是加工产物。原始数据的许可允许演绎和再发布的（如 CC-BY），产物可以进仓库，并注明出处和许可；不允许演绎或再发布的（如 ND 条款），产物不进仓库，只公布分数和产物的 sha256。
- 自有或私有会话的产物一律不公开。

### 12.3 每个模型都要记录的参数

适用于所有用到模型的环节：被测对象使用的 LLM 和向量模型、标注模型、判定模型。

| 项 | 内容 |
|---|---|
| 提供方和接口 | 例如某云的 OpenAI 兼容接口、某 CLI |
| 模型 | 模型 id，有快照或日期版本的写到快照 |
| 调用工具及版本 | 通过 CLI 调用的，记录 CLI 的版本号 |
| 推理参数 | 推理强度、温度、top_p、seed（支持时）、最大输出长度 |
| 上下文 | 模型的最大上下文长度；本次实际输入的长度（token 数，或者明确标为字符估算）；**有没有被截断、截断了多少** |
| 提示词 | 提示词文件的版本号和 sha256；系统提示词（如有） |
| 运行环境 | 沙箱或权限设置、联网与否、调用时间（UTC） |
| 失败与重试 | 每个样本的重试次数、最终失败的样本清单 |

向量模型另外记录：维度、是否归一化、分块规则。

### 12.4 运行清单

每次运行的环境与审计信息保存在产物内的身份记录或独立 manifest 中；公开范围遵循 12.2 节。记录内容包括：

- 本仓库的 commit、Python 版本、操作系统；
- 框架版本、政策 id 和版本、数据集清单的版本；
- 12.3 节的全部模型参数；
- 处理了哪些样本，每个样本的输入和输出 sha256；
- 原始输出（例如 CLI 的完整返回）的存放位置及 sha256。原始输出体积大的可以只在本地保存，仓库里只记哈希。

报告头部引用这些运行清单。缺了某一项的，报告里明确写“未记录”，不能省略。
