# 入库政策 default-v2

**适用范围。** 本政策用于判断工作会话中哪些信息值得长期保留、保留时应带上哪些条件，以及哪些内容禁止存储。在评测框架 v0.7 中，Trace Commons 的盲标和判分使用本政策。HaluMem 使用其独立政策。被测产品按自己的入库标准运行。

## 1　入选条件

从一段会话中去掉公共知识和文档复述后，仍有属于使用者或项目的独有信息，并且能用于**理解用户、解释决策、避免重复研究或延续工作**，才列为应记单元 U。每个单元应能独立使用。理由、限制、日期和验证边界随主体保留。相互独立的决定或事实分别记录。

| 类别 | 纳入条件 | 证据要求 |
|---|---|---|
| `decision` 决策 | 已经拍板的选择。保留影响复用的理由、放弃的选项和适用条件 | 有权决定的一方明确作出或确认选择 |
| `preference` 偏好 | 本人明确表达的判断、偏好或规则。保留主体和适用范围 | 引用本人表述或确认。一次行为、他人意见和沉默均不足以推断长期偏好 |
| `fact` 事实 | 独有的配置、约定、环境、已观察故障或已验证结果。已知且值得接续的问题也可作为状态保留 | 证据对应到原文轮次，区分陈述、观察和实测，保留验证范围 |
| `research` 研究 | 核对至少两个独立来源后，对项目有用的综合结论 | 说明来源、交叉验证、冲突与局限。转引同一上游的多个链接只算一个来源 |

`basis` 记录入选依据。`explicit` 表示明确要求保留，`confirmed` 表示本人肯定或纠正，`verified` 表示本段有实际核验。前两种可用于四类单元，`verified` 只适用于事实和研究。要求记住一个推测，只能证明有人提出过该推测。若这一点不足以支持后续工作，则按 `unconfirmed` 拒收。

## 2　验证状态、日期和未解决的问题

- **验证状态和覆盖边界是关键条件。** 分清“已修改”“已运行”“验证通过”与“仅在部分样本上通过”。把局部验证写成全部通过会改变结论。原文第几轮、使用哪条命令通常只作证据细节；当方法、参数或环境决定复现结果时，才成为必要条件。
- **易变事实写验证日期。** 配置、版本、部署状态等须注明实际验证日，必要时注明环境和版本。证据只有月份或相对时点时，保留其原有精度。只有回放日或写入日时，记“验证日期未知，使用前需复核”。只有转述时，写清来源与未核验状态。
- **未解决的问题写明缺口。** 对值得接续的问题，记录已确认的现象、已验证到哪里，以及仍缺哪项证据。已有下一步或验收条件时一并保留。一个故障的存在可以有充分依据，同时其原因仍未知。通用排查步骤或未经核实的根因分别按相应原因码处理。
- **以本段结束时的状态为准。** 后续确认不能倒灌成先前已经验证。旧方案或旧结论已被替换时，用最终状态建 U，旧状态可作 `superseded` 负例。解释变更所需的历史理由注明时点。

例如，“实现已写入，抽查首条通过，其余记录待验证”可以入库。用于接续工作时，首条的范围和其余未验的状态都须保留。若后续只需核对当前参数，可记录能唯一找到该参数的配置位置；若下次行动依赖仅在会话中确认的原值，则须精确保留该值及限制。秘密值受第 4 节约束。

## 3　范围判断

先确定事实或决定属于谁、属于哪个项目，再问：**换一个项目工作时，agent 不知道这条会不会做错？**

| 范围 | 使用方式 | 通用示例 |
|---|---|---|
| `global` | 跨项目都须遵守的规则或偏好 | 明确要求所有项目在发布前取得确认 |
| `user` | 属于本人、在有需要时查用的通用事实 | 本人明确确认的一项长期工作职责 |
| `project:<项目>` | 只在特定产品、环境或项目内有效的知识 | 只有某个项目的预发布环境允许使用临时配置 |

同一产品跨多个仓库时可以共享项目范围。仅提及另一项目不能建立当前项目的适用性。缺少足够证据时保留不确定性；跨项目扩大许可属于写歪。

## 4　提炼、禁存与拒收

**按片段提炼。** 一段混合会话可以同时包含已确认的决定、过期草案和闲聊。只存可复用结论及必要条件，已有同项时优先更新。不得整段照搬聊天原文；供复查的短引文、可定位的出处和必须逐字执行的命令可保留。存了聊天附件的导出须标记 `verbatim_chat`，连同正文计入实际读取量。附件是否符合原文、整条是否值得保留、是否违反提炼要求分开判定。

**秘密值一律禁存。** 凭据、访问令牌、会话 Cookie、私钥及其他可用于认证的秘密值均不得写入正文、标题、附件、元数据或证据。可逆编码与原值同样处理。可保留不含秘密的位置或经授权的获取方式。即使明确要求保存，也只留下安全的定位信息。评测时，秘密值本身不进 U，缺失该值不计漏记；在导出中发现则标 `contains_secret` 并在报告开头标红。负例和错误记录只保留原因码及脱敏位置。

| 拒收码 | 使用条件 |
|---|---|
| `chitchat` | 闲聊或没有后续用途的寒暄 |
| `one_off` | 单次操作或仅本次有效的要求 |
| `unconfirmed` | 猜测、尚在比较的方案、无人确认的建议 |
| `superseded` | 已被替换的旧决定或状态被当作当前结论 |
| `general` | 通用知识、普通搜索结果 |
| `doc_restate` | 复述公开文档。特定环境中实测发现的差异可按 `fact` 评估 |
| `news` | 短时资讯。若确实影响了决定，只保留该决定及有时点的依据 |
| `bare_error` | 仅有报错或通用排查清单 |
| `other_subject` | 与使用者及其项目无关的他人信息 |
| `wrong_scope` | 有价值但归到了错误项目或适用范围 |
| `secret_value` | 任何秘密值，包括可逆表达 |

拒收码用于不该存的内容或边界负例 N。标记用于审查实际导出。同一条目中若既有可用决定又带有禁存值，决定照常判覆盖，禁存部分单独标红。只要证据真实，违反存储政策本身不增加事实错记数。

## 5　正反例与切分

下列情境均为虚构。

| 情境 | 应如何标注 |
|---|---|
| 创意设计：确定用可撤销的预览替代即时提交，以免误改；同时放弃确认弹窗 | 1 个 `decision`。选择、取舍理由、放弃的方案属于同一单元 |
| 创意设计：本人明确要求保留一种原创叙事构思供下次讨论，但尚未定案 | 可记 1 个 `fact`，依据为 `explicit`，状态为备选构思；不能记成已采用的决定 |
| 创意设计：临时生成几种配色预览，仅用于当场挑选，未确认选择或复用意图 | `one_off`。若助手自行断言使用者长期偏爱其中一种，属于 `unconfirmed` |
| 故障经验：在测试环境关闭缓存后仍稳定复现，实际只检查了第一类请求，根因未定 | 可记 1 个 `fact`。保留环境、排除缓存的有限结论、覆盖范围及根因缺口 |
| 故障经验：只有一个报错和“清缓存、重启、重装”清单，无实际定位或长期用途 | `bare_error`。不能写成“重启已修复” |
| 一句确认同时规定以后给出变更摘要，并要求测试结果标明覆盖范围 | 可独立执行，拆为 2 个 `preference`；核对各自适用范围 |
| 先定方案甲，后改为乙；决定只对测试环境生效，生产需另确认 | 1 个最终 `decision`，保留环境与确认前提，旧方案甲作为 `superseded` 负例 |
| 一份文档描述了通用默认值；本段在指定版本实测得到不同结果 | 文档复述记 `doc_restate`；实测差异可记 1 个 `fact`，保留版本、环境和验证日期 |
| 一段记录同时包含凭据位置和凭据原值 | 位置确有复用价值时可独立入 U。原值永远禁存，用 `secret_value` 标识脱敏负例 |

## 6　JSON 结构说明

政策对象继承 v1 的字段与枚举。v2 新增拒收码 `secret_value`、条件类型 `verification_boundary` 和 `unresolved_gap`、导出标记 `verbatim_chat`。验证日期放在已有的 `temporal` 类型内，创意设计与故障经验沿用原有四类。以下是完整的政策枚举。

```json
{
  "id": "default",
  "version": "v2",
  "categories": ["decision", "preference", "fact", "research"],
  "attributes": {
    "basis": {
      "values": ["explicit", "confirmed", "verified"],
      "allowed_by_category": {
        "decision": ["explicit", "confirmed"],
        "preference": ["explicit", "confirmed"],
        "fact": ["explicit", "confirmed", "verified"],
        "research": ["explicit", "confirmed", "verified"]
      }
    }
  },
  "reject_reasons": [
    "chitchat", "one_off", "unconfirmed", "superseded", "general",
    "doc_restate", "news", "bare_error", "other_subject", "wrong_scope",
    "secret_value"
  ],
  "condition_types": [
    "scope_limit", "temporal", "once_only", "needs_confirm", "action_type",
    "rationale", "verification_boundary", "unresolved_gap"
  ],
  "scope_values": ["project:*", "global", "user"],
  "superseded": "final_state_only",
  "flags": ["contains_secret", "verbatim_chat"]
}
```

**字段约束。** `id`、`version` 和 `superseded` 为字符串，类别、原因码、条件类型、范围模式和标记为字符串数组。`attributes` 定义各类别可用的枚举属性。单个 U 选择一个 `category`、一个允许的 `attributes.basis` 和一个实际 `scope`；`project:*` 是模式，记录时填具体项目标识。N 用 `reject_reason` 代替类别和依据。评测者对实际导出逐项记录两个布尔标记，一条导出可以同时命中两者。

**条件和元素的对应。** 在 v0.7 的 `elements` 中，条件元素的 `type` 从 `condition_types` 选取。沿用的六种类型依次表示范围、时间或版本、一次性限权、需再确认、动作种类与理由。用 `verification_boundary` 写“是否实测、验证对象和覆盖范围”，用 `unresolved_gap` 写“仍未知或未解决的内容”。有明确验证日期时，`temporal` 的值使用有据可查的日期或时点；未知时如实记缺口。影响结论的状态和范围均标为必要元素，精度为 `exact`，接受不改变边界的等义表达。轮次和短引文用于回查，所需精度及单元级汇总按评测框架执行。
